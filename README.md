**1. [Lunar Seeker : Bound!] - 2D 액션 플랫포머 완성작 프로젝트**

* Godot Engine으로 개발한 2D 액션 플랫포머 게임입니다. 1인 개발로 기획, 프로그래밍, 리소스 구성, 출시, 유지보수까지 진행했으며, FSM 기반 플레이어 컨트롤, 컴포넌트 기반 구조, JSON 대화 시스템, 저장/불러오기 시스템 등을 직접 설계 및 구현했습니다.
프로젝트 규모가 커지면서 코드 간 결합도가 높아지는 문제를 줄이기 위해 컴포넌트 기반 설계를 도입했습니다. 또한 Singleton(Autoload)과 시그널 패턴을 활용하여 데이터 영역과 UI 영역을 분리했고, 1만 줄 이상의 코드에서도 기능 확장과 유지보수가 가능하도록 구조를 정리했습니다.
플랫포머 조작감을 개선하기 위해 코요테 타임, 선입력 버퍼, 모서리 보정, 가감속/마찰력 등을 직접 구현했습니다. 이를 통해 플레이어가 입력 지연이나 판정 불쾌감을 덜 느끼도록 조작 경험을 보정했습니다.

**5. 핵심 기술 구현 사항**

**FSM 기반 플레이어 컨트롤러**

* 플레이어의 이동, 점프, 공격, 가드, 피격 등의 상태를 FSM 패턴으로 분리하여 관리했습니다. 각 상태의 진입, 갱신, 종료 로직을 분리하여 플레이어 액션이 복잡해져도 흐름을 추적하기 쉽게 구성했습니다.

* 플레이어 조작감을 개선하기 위해 다음 기능을 구현했습니다.

코요테 타임 : 발판에서 살짝 벗어난 직후에도 짧은 시간 동안 점프가 가능하도록 유예 시간을 부여했습니다.
선입력 버퍼 : 착지 직전에 점프 입력을 받으면, 착지 후 즉시 점프가 실행되도록 처리했습니다.
가감속 / 마찰력 : acceleration과 friction 값을 활용하여 이동 시작과 정지를 자연스럽게 처리했습니다.
모서리 보정 : 점프 중 머리 위쪽 모서리에 걸렸을 때 캐릭터 위치를 보정하여, 작은 지형 충돌 때문에 점프 흐름이 끊기지 않도록 했습니다.
스쿼시 앤 스트레치 : 점프와 착지 시 캐릭터 스프라이트의 크기를 Tween으로 조절하여 시각적인 탄력감을 추가했습니다.

**패링 및 퍼펙트 가드 전투 시스템**

* 전투의 타격감과 방어 타이밍의 재미를 살리기 위해 패링, 퍼펙트 가드, 히트스탑을 구현했습니다.

* CombatBody2D 기반 공통 전투 구조 : 체력, 무적 시간, 깜빡임, 넉백 저항, 피격 쿨타임 등을 처리하는 공통 전투 클래스를 만들고, 플레이어와 적이 이를 공유하도록 설계했습니다. 이를 통해 피격 처리, 파티클 스파크, 피격 효과를 중복 구현하지 않도록 했습니다.
퍼펙트 가드 : 플레이어가 가드 상태에 진입한 직후 짧은 시간 안에 투사체를 막으면 데미지를 무효화하고 보너스를 얻도록 구현했습니다.
히트스탑 : 공격 성공, 패링 성공, 퍼펙트 가드 성공 시 GameManager.apply_hitstop을 호출하여 Engine.time_scale을 짧게 낮추고, 타격 순간의 손맛을 강화했습니다.

**싱글톤 기반 전역 상태 및 게임 매니저**

* Singleton(Autoload)을 활용하여 게임 전역 상태를 관리했습니다.

* 데이터 관리 : 체력, 돈, 인벤토리, 처치한 보스/몬스터 목록, 상호작용한 NPC 대화 기록 등을 GameManager에서 관리했습니다.
시그널 기반 UI 동기화 : 데이터가 변경될 때 UI를 직접 수정하지 않고, 시그널을 발행하여 UI 씬이 스스로 갱신되도록 구성했습니다. 이를 통해 데이터 로직과 UI 로직의 결합도를 낮췄습니다.
세이브 연동 : 현재 게임 상태를 Dictionary 형태로 정리해 SaveManager에 전달하고, 로드 또는 부활 시 마지막 체크포인트 위치와 씬으로 이동하도록 처리했습니다.

**JSON 기반 대화 및 선택지 시스템**

* 대사를 코드에 직접 작성하지 않고, 외부 JSON 파일에서 읽어오는 방식으로 대화 시스템을 구현했습니다. 이를 통해 대사 수정, 분기 추가, 조건부 선택지 추가를 코드 수정 없이 처리할 수 있도록 구성했습니다.

* 포트레이트 연출 : 왼쪽/오른쪽 초상화를 출력하고, 현재 말하는 화자를 강조하기 위해 말하지 않는 쪽은 어둡게 처리했습니다. 말하는 캐릭터는 Tween을 사용해 살짝 움직이도록 연출했습니다.
조건부 선택지 : 선택지마다 조건을 설정할 수 있도록 구성했습니다. 돈 보유 여부, 특정 아이템 보유 여부, 보스 처치 여부 등을 GameManager에서 확인하고, 조건을 만족하지 못하면 선택지를 비활성화했습니다.

**리소스 기반 아이템 구조**

* 아이템 데이터를 코드 내부 딕셔너리로 관리하지 않고, Godot의 Resource를 활용하여 분리했습니다.

* ItemData 리소스 : 아이템 이름, 아이콘, 설명, 가격, 타입 등을 커스텀 Resource로 정의했습니다. 이를 통해 에디터 인스펙터에서 아이템 데이터를 쉽게 생성하고 수정할 수 있도록 만들었습니다.
아이템 효과 캡슐화 : 아이템 타입에 따라 체력 회복, 최대 체력 증가, 공격력 증가, 패링 배율 증가 등의 효과를 분기 처리했습니다. 아이템 관련 정보를 한 곳에서 관리하여 수정과 확장이 쉽도록 구성했습니다.

**저장 / 불러오기 시스템**

* 플레이어의 진행 상황을 저장하고 다시 불러올 수 있도록 SaveManager를 구현했습니다.

* 체력, 돈, 인벤토리, 체크포인트 위치, 현재 씬, 처치한 몬스터/보스 정보, NPC 대화 진행 상태 등을 저장 대상으로 관리했습니다.
저장 데이터를 Dictionary 형태로 구성한 뒤 JSON으로 변환하여 파일에 기록했습니다.
로드 시 저장된 씬과 체크포인트 정보를 기반으로 플레이어를 복귀시키고, 게임 진행 상태를 복원하도록 처리했습니다.

**6. 트러블 슈팅 히스토리**

**몬스터 지형 인식 예외 및 플랫폼 이탈 이슈**

* 순찰 상태의 몬스터가 특정 플랫폼 끝단이나 가시 지형을 제대로 감지하지 못하고 떨어지는 문제가 있었습니다.

* 기존에는 단일 downward RayCast에 의존하고 있었기 때문에, 일반 발판과 데미지를 주는 지형을 정밀하게 구분하지 못했습니다. 그 결과 몬스터가 위험 지형을 안전한 지형으로 판단하거나, 플랫폼 끝을 늦게 감지하는 문제가 발생했습니다.

* 이를 해결하기 위해 RayCast의 감지 범위를 몬스터 이동 속도에 맞게 조정하고, 감지된 충돌 대상의 레이어와 데미지 컴포넌트 보유 여부를 함께 검사하도록 수정했습니다. 위험 지형을 감지하면 즉시 이동 방향을 반전하도록 예외 처리를 추가하여 플랫폼 이탈 문제를 줄였습니다.

* 이 경험을 통해 단순한 충돌 감지만으로는 AI 이동을 안정적으로 처리하기 어렵고, 지형의 속성과 몬스터의 이동 속도를 함께 고려해야 한다는 점을 배웠습니다.

**JSON 직렬화 / 역직렬화 데이터 무결성 오류**

* 저장 및 불러오기 시스템을 반복해서 테스트하는 과정에서 저장 파일 파싱 실패로 인한 런타임 오류가 발생했습니다.

* 원인은 수동 문자열 결합과 파싱 과정에서 발생한 오타 및 데이터 타입 불일치였습니다. 컴파일 단계에서는 문제가 드러나지 않았지만, 런타임에서 저장 데이터의 구조가 깨지면서 로드 과정이 실패했습니다.

* 이를 해결하기 위해 저장 데이터 구조를 다시 점검하고, 수동 문자열 처리 대신 Godot의 JSON 관련 API를 사용해 직렬화 / 역직렬화 과정을 정리했습니다. 또한 저장 대상 데이터를 1:1로 검증하여 누락되거나 타입이 맞지 않는 항목을 수정했습니다.

* 이 경험을 통해 저장 시스템에서는 데이터 구조의 일관성과 타입 검증이 중요하다는 점을 배웠습니다.

**Autoload 초기화 순서로 인한 UI 초기화 실패 이슈**

* 미니맵, 인벤토리 등 HUD UI가 생성될 때 입력 이벤트가 정상적으로 동작하지 않거나, 일부 UI 컴포넌트가 렌더링되지 않는 간헐적 문제가 있었습니다.

* 원인은 Autoload로 등록된 싱글톤 노드들의 초기화 순서였습니다. UI 씬이 생성되는 시점에 참조해야 할 데이터 매니저가 아직 준비되지 않아, null 참조 계열의 문제가 발생했습니다.

* 이를 해결하기 위해 Godot 프로젝트 설정에서 Autoload 등록 순서와 의존 관계를 정리했습니다. 데이터 매니저가 UI보다 먼저 초기화되도록 구조를 조정하고, UI는 데이터를 직접 가져오기보다 시그널을 구독하여 안전하게 갱신되도록 수정했습니다.

* 이 경험을 통해 전역 매니저를 사용할 때는 단순히 접근 가능 여부만이 아니라, 초기화 순서와 UI의 구독 시점을 함께 관리해야 한다는 점을 배웠습니다.
